# نقشه راه اجرای «دنگ همکاری ۲.۰» + قوانین حاکمیتی پروژه

این سند مکمل «سند جامع محصول و معماری» است. اینجا مشخص می‌کنیم **به چه ترتیبی** بسازیم، و **چه قوانینی** رعایت بشه تا با رشد فیچرها، همون مشکلاتی که در سه دور تحلیل قبلی دیدیم (گیت نرم، فایل غول‌پیکر، سند/کد ناهم‌خوان، فیچر ظاهری بدون پشت‌صحنه‌ی واقعی) دوباره تکرار نشه.

---

## بخش الف — قوانین حاکمیتی (قبل از نوشتن اولین خط کد فیچر جدید بخوانید)

این قوانین از سه دور تحلیل واقعی این پروژه استخراج شدن — هرکدوم پاسخ به یک اتفاق واقعی‌ست که قبلاً افتاده:

### قانون ۱ — هیچ گیتی حق «skip بی‌صدا» ندارد
اگر یک تست/چک به هر دلیلی (نبود Chrome، نبود DATABASE_URL، …) نمی‌تونه اجرا بشه، باید **fail** کنه، نه این‌که پیام چاپ کنه و سبز رد بشه. اگر skip شدن گاهی واقعاً لازمه (مثلاً محیط لوکال بدون Redis)، باید یک annotation صریح در خروجی CI بذاره که در PR review دیده بشه. *(ریشه: تست cross-tenant که قبلاً بی‌صدا skip می‌شد.)*

### قانون ۲ — هر گیتی باید Scope خودش را صریح اعلام کند
وقتی یک گیت (مثل بودجه‌ی خط یا coverage) روی یک زیرمجموعه‌ی محدود اجرا می‌شه، اسمش در CI باید این محدودیت رو نشون بده (مثل «coverage — finance-focused» که الان دارید)، و یک بار در ماه بررسی بشه که آیا فایل/ماژول جدیدی از دایره‌ی دید این گیت جا مونده. *(ریشه: `view-line-budget` که فقط `components/views/` را می‌بیند نه کل `components/`.)*

### قانون ۳ — هیچ Entity مالی جدید بدون سه‌گانه‌ی «Migration + RLS + Invariant Test» مرج نمی‌شود
هر جدول جدید که پول/تراز/تسویه رو نگه می‌داره (مثل `personal_addon_charge`, `financial_resource`) باید همزمان با: (۱) مایگریشن دیتابیس، (۲) پالیسی RLS، (۳) حداقل یک تست invariant (مثل zero-sum) بیاد — نه این‌که «فعلاً بدون RLS بسازیم، بعداً اضافه می‌کنیم». *(ریشه: قدرت اصلی این پروژه دقیقاً در انضباط RLS/ledger بوده؛ نباید با فیچر جدید نقض بشه.)*

### قانون ۴ — سند و کد همیشه با هم مرج می‌شوند
اگر یک فیچر در `docs/` ادعا می‌شه، باید در همون PR کد واقعی‌ش هم باشه. اگر یک تصمیم موقتاً محدوده (مثل i18n scaffold)، سند باید صریح بگه «این فقط scaffold است، منبع حقیقت نیست» — دقیقاً مثل کاری که با `docs/I18N.md` قبلاً درست انجام دادید. *(ریشه: مغایرت اولیه‌ی SECURITY.md با کد واقعی.)*

### قانون ۵ — بودجه‌ی خط برای همه‌ی کامپوننت‌ها، نه فقط پوشه‌ی فعلی
هر فایل UI جدید (چه در `components/views/` چه در `components/` یا هر پوشه‌ی جدید مثل `components/finance/`) مشمول همون سقف WARN=800/FAIL=1600 است. قبل از اضافه‌کردن این فیچر بزرگ (که قطعاً فایل‌های UI زیادی میاره)، اول scope گیت `view-line-budget` باید به کل `apps/web/src/components/**` گسترش پیدا کنه.

### قانون ۶ — هیچ فیچری «فقط UI» تحویل داده نمی‌شود
یک دکمه/فرم/صفحه که پشت‌صحنه‌اش API واقعی، دیتابیس واقعی، و تست واقعی نداره، در Definition of Done به‌عنوان «ناتمام» علامت می‌خوره، حتی اگر ظاهرش کامل باشه. اگر لازمه یک نسخه‌ی نمایشی زودتر دیده بشه، باید صریح با برچسب «پیش‌نمایش — بدون داده‌ی واقعی» مشخص بشه. *(این مستقیماً پاسخ به نگرانی خود شما در این پیام است: «الکی خراب یا کند یا ظاهری نباشه».)*

### قانون ۷ — هر ماژول جدید، مسیر «تشخیص کندی» را از روز اول دارد
هر کوئری تجمیعی جدید (BI/گزارش) از ابتدا با `EXPLAIN ANALYZE` بررسی و در PR مستند بشه که روی داده‌ی حجیم (نه فقط داده‌ی تست ۱۰ ردیفی) چطور رفتار می‌کنه. رفتن به Materialized View/CQRS فقط با شواهد واقعی کندی، نه حدس (طبق بخش ۶.۴ سند اول).

### قانون ۸ — هر صفحه‌ی جدید همان لحظه وارد گیت a11y می‌شود
نه در فاز جداگانه‌ی «بعداً دسترس‌پذیری». لیست مسیرهای `a11y-shell.spec.ts` باید در همون PR که صفحه اضافه می‌شه، به‌روز بشه.

### قانون ۹ — نقش «مدیر مالی» همیشه حداقل دو نفر پشتیبان دارد (در سطح دیتابیس enforce می‌شود)
یک workspace با `type IN ('friends_group','family','organization')` نباید بتونه در وضعیتی قرار بگیره که فقط یک نفر نقش Treasurer داشته باشه و آن نفر غیرفعال/حذف بشه — این باید یک constraint یا حداقل یک چک اپلیکیشنی سخت‌گیرانه باشه، نه فقط توصیه در UI.

## بخش ب — نقشه راه فازبندی‌شده

```
فاز A ── مدل داده و دامنه (پیش‌نیاز مطلق)
  │
  ├──► فاز B ── موتور هزینه‌ی مشترک + add-on شخصی (قلب محصول)
  │        │
  │        └──► فاز C ── تسویه‌حساب هوشمند (Debt Simplification)
  │
  ├──► فاز D ── موتور تکرار (Recurring) — موازی با B/C ممکن است
  │
  ├──► فاز E ── گزارش‌گیری/BI — بعد از این‌که B/D داده‌ی واقعی تولید می‌کنن معنا دارد
  │
  ├──► فاز F ── تفاوت‌های خانوادگی/سازمانی (حریم خصوصی، تأیید، Cost Center)
  │
  └──► فاز G ── بازطراحی IA/ناوبری برای بازتاب همه‌ی موارد بالا
```

### فاز A — مدل داده و دامنه (۱-۲ هفته)

- مایگریشن‌های جدید: `expense_category`, `personal_addon_charge`, `financial_resource`, `recurrence_rule` (طبق بخش ۶.۱ سند اول).
- RLS برای هر جدول جدید همان لحظه (طبق قانون ۳).
- `workspace.type` اضافه بشه به schema موجود اگر نیست؛ migration برای مقداردهی پیش‌فرض به فضاهای موجود (`friends_group` برای همه‌ی workspaceهای فعلی، چون این پیش‌فرض فعلی سیستمه).
- تعریف نقش `Treasurer` در `iam` module موجود + قانون ۹ (حداقل دو نفر پشتیبان).
- **Definition of Done فاز A:** یک تست integration که یک workspace کامل با هر ۴ نوع تراکنش (مشترک، add-on، شخصی، درآمد) بسازه و invariant اصلی (بخش ۴.۳ سند اول: `invoice_total = Σallocation + Σaddon`) رو در سطح DB و اپلیکیشن چک کنه.

### فاز B — موتور هزینه‌ی مشترک + Add-on شخصی (۲-۳ هفته)

- گسترش `expenses` module موجود برای پشتیبانی از ۵ روش تقسیم (equal/percentage/exact/shares/itemized) — منطق محاسبه در `packages/contracts` (pure function، تست‌شده، دقیقاً مثل الگوی فعلی `finance.ts`).
- ماژول جدید برای `personal_addon_charge` با state machine: `pending_ack → confirmed` یا `disputed → resolved` (طبق نیازمندی ۵.۱ سند اول).
- Zod schema برای همه‌ی endpoint های جدید از روز اول (نه بعداً اضافه کردن).
- فرم UI طبق بخش ۷.۳/۷.۴ سند اول — با تفکیک بصری واضح بین دو نوع هزینه.
- **Definition of Done فاز B:** یک عضو نمی‌تونه add-on شخصی دیگری رو بدون تأیید صریح در صورتحساب نهایی‌اش ببینه؛ تست e2e این سناریو رو پوشش بده.

### فاز C — تسویه‌حساب هوشمند (۱ هفته، وابسته به B)

- پیاده‌سازی الگوریتم debt-simplification (greedy: بزرگ‌ترین بستانکار در برابر بزرگ‌ترین بدهکار) در `packages/contracts` با سه قانون طلایی (بخش ۴.۵ سند اول) به‌عنوان تست invariant.
- UI پیشنهاد مسیر تسویه («به‌جای ۳ پرداخت، فقط ۱ پرداخت کافیه»).
- **Definition of Done:** تست unit که تضمین کنه بعد از simplification، مانده‌ی خالص هر عضو بدون تغییر می‌مونه (فقط مسیر پرداخت عوض می‌شه).

### فاز D — موتور تکرار (۱-۲ هفته، می‌تواند موازی B/C شروع شود)

- `recurrence_rule` + job جدید `recurrence-tick` در `apps/worker` (طبق بخش ۶.۳ سند اول).
- منطق `auto_confirm` true/false.
- اعلان یادآوری (استفاده از زیرساخت notification موجود).
- **Definition of Done:** یک تست worker که یک قانون ماهانه رو با تاریخ شبیه‌سازی‌شده (نه صبر واقعی یک ماه) تریگر و رکورد جدید تولید کنه؛ تست DLQ برای حالت شکست.

### فاز E — گزارش‌گیری و BI (۲-۳ هفته، بعد از این‌که B/D داده‌ی واقعی تولید می‌کنن)

- شروع با SQL View ساده (طبق قانون ۷، نه Materialized از روز اول).
- دشبورد سه‌لایه (بخش ۷.۵ سند اول): یک‌نگاه، روند، جزئیات.
- بودجه‌بندی و هشدار سقف دسته (۵.۳).
- Export کامل Excel/CSV.
- **Definition of Done:** یک تست performance با داده‌ی سینتتیک حجیم (مثلاً ۱۰٬۰۰۰ تراکنش) که تأیید کنه صفحه‌ی گزارش زیر یک آستانه‌ی زمانی مشخص (مثلاً ۱ ثانیه) لود می‌شه؛ اگر نه، طبق قانون ۷ به Materialized View برید.

### فاز F — تفاوت‌های خانوادگی/سازمانی (۲-۳ هفته)

- حریم خصوصی per-item برای `family` (بخش ۵.۴).
- گردش کار تأیید (`approval_workflow_step`) برای `organization` (بخش ۵.۵).
- Cost Center/پروژه.
- درخواست بازپرداخت (Reimbursement) با state machine جدا.
- **Definition of Done:** تست RLS که تأیید کنه یک عضو خانواده بدون اجازه، هزینه‌ی خصوصی عضو دیگر رو نمی‌بینه، حتی با query مستقیم.

### فاز G — بازطراحی IA/ناوبری (۱-۲ هفته، در کنار فازهای بالا به‌مرور)

- ناوبری جدید طبق بخش ۷.۱ سند اول.
- به‌روزرسانی `docs/IA.md` با مسیرهای جدید.
- گسترش گیت a11y به همه‌ی صفحات جدید (طبق قانون ۸، همزمان با ساخت هر صفحه، نه در این فاز جدا).

## بخش ج — ترتیب پیشنهادی اجرا (Sequencing نهایی)

با توجه به وابستگی‌ها، ترتیب واقع‌بینانه:

1. **فاز A** (اجباری، همه چیز به آن وابسته است)
2. **فاز B + C با هم** (قلب تجربه‌ی کاربر — بدون این دو، بقیه بی‌معناست)
3. **فاز D** (می‌تواند تیم دوم موازی روی آن کار کند، وابستگی کمی به B/C دارد)
4. **فاز G (بخش ناوبری اولیه)** — همزمان با B/C، چون UI جدید همان لحظه باید در ساختار درست بنشیند، نه بعداً منتقل شود
5. **فاز E** (فقط بعد از این‌که B/D داده‌ی واقعی برای گزارش‌گیری تولید کردند — گزارش‌گیری روی داده‌ی خالی بی‌فایده است)
6. **فاز F** (آخرین، چون خاص‌ترین و کم‌تکرارترین سناریوهاست؛ محصول بدون آن هم برای گروه دوستانه/شخصی کامل کار می‌کند)

## جمع‌بندی

این نقشه راه عمداً «قلب محصول» (تقسیم هزینه + add-on شخصی + تسویه) را قبل از «تزئینات» (BI پیشرفته، سازمانی) قرار داده، چون این همان چیزی‌ست که شما به‌عنوان نیاز اول گفتید و همان چیزی‌ست که در هیچ رقیبی (بخش ۱ سند اول) به این شکل دقیق وجود ندارد. قوانین حاکمیتی بخش الف هم مستقیماً از تجربه‌ی واقعی سه دور تحلیل قبلی این پروژه گرفته شدن — نه توصیه‌ی عمومی، بلکه پاسخ به اتفاقاتی که واقعاً افتاده بودن.
